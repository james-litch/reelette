# Local development

[Back to README](../README.md)

## Google sign-in

1. Create a **Web application** OAuth client in
   [Google Auth Platform](https://console.cloud.google.com/auth/overview).
   Configure the consent screen, enable `openid`, `userinfo.email`, and
   `userinfo.profile`, and add your account as a test user when required.
2. Set the JavaScript origin to `http://localhost:3000` and register
   `http://127.0.0.1:54321/auth/v1/callback` as an authorized redirect URI.
3. Copy [`.env.example`](../.env.example) to `.env` and fill in
   `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID` and
   `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_SECRET`.
4. Start Supabase and the app using the [quick start](../README.md#run-locally).
   After changing OAuth credentials or [config.toml](../supabase/config.toml),
   stop and start Supabase to reload Auth.

Google returns to Supabase, which redirects to the app's `/auth/callback`.
The app exchanges the PKCE code for a cookie-based session; `proxy.ts` refreshes
sessions, and server-side access checks verify the user with Supabase Auth.

## Environment

- `.env`: local Supabase Google OAuth credentials and optional `SEED_OWNER_EMAIL`.
- `.env.local`: `TMDB_ACCESS_TOKEN` and, optionally, hosted Supabase public values.
- `.env.development.local`: local public Supabase URL/key generated by
  `npm run supabase-env`. It takes precedence during development.

Keep credentials out of git. `TMDB_ACCESS_TOKEN` is server-only and must never
have a `NEXT_PUBLIC_` prefix. The app does not require a service-role key.
The local API is at `http://127.0.0.1:54321`; sign in again when switching environments.

## Database commands

```bash
npm run supabase-db-migrate  # Apply pending local migrations
npm run supabase-db-seed     # Create/restore the test room and member
npm run supabase-types       # Regenerate public database types
npm run supabase-db-test     # Run SQL checks; fixtures roll back
npm run supabase-stop        # Stop services and preserve data
npm run supabase-db-reset    # DELETE local data, replay migrations, and seed
```

The CLI is installed with npm dependencies. SQL checks use `psql` inside the
local Docker container; no host PostgreSQL installation is needed. Test suites
live in [supabase/tests](../supabase/tests); the npm script defines which run.

After schema changes, apply migrations, regenerate
[database.types.ts](../lib/supabase/database.types.ts), and commit SQL and types
together. `npm run supabase-db-pull` reads the linked hosted schema; it does not
apply local changes to production. See [deployment](deployment.md) for that workflow.

## Seed data

Set the owner email in the root `.env`:

```dotenv
SEED_OWNER_EMAIL=you@example.com
```

[seed.sql](../supabase/seed.sql) creates a **Test** room owned by that account,
with **Test Member** (`test-member@example.com`) as its other participant.
Sign in with the owner's Google account to test removal. The test member has
no password and does not need to sign in.

`npm run supabase-start` and `npm run supabase-db-reset` seed fixtures when configured;
CI and direct Supabase CLI commands skip personal fixtures. After using the CLI
directly, run `npm run supabase-db-seed` to create them. Shell variables override
`.env`; this variable is not needed in production.

Existing accounts are reused by email. After a reset, confirmed email identities
allow Google to link the owner on sign-in; no OAuth tokens or sessions are seeded.
Rerun `npm run supabase-db-seed` to restore the removed test member without
resetting other data. This also restores the fixture room's name and owner.
